# Blind SQL injection with time delays

## 문제 조건과 설명

방문자 분석에 쓰는 추적 쿠키의 값이 SQL 조회에 들어간다. 조회 결과는 응답에 보이지 않고, 반환 행이 달라지거나 SQL 오류가 나도 페이지 응답은 구별되지 않는다. 앞선 문구·오류 기반 실습에서 쓰던 신호가 없는 셈이다. 다만 공식 설명은 **SQL 조회가 동기식으로 실행된다**고 명시한다.

**동기식 실행이 왜 단서인가**

동기식이라면 서버가 해당 조회를 마치기 전까지 요청 처리를 끝내지 못한다. 따라서 조회 안에서 지연이 발생하면 응답 본문이 같더라도 **응답까지 걸린 시간**은 달라질 수 있다. 이 실습은 숨겨진 데이터의 값을 찾기보다, 화면 변화가 없는 상황에서 시간이라는 관찰 경로를 만들 수 있는지 확인하는 단계다.

**완료 조건은 SQL injection으로 응답에 10초 지연을 발생시키는 것**이다. 단순히 한 요청이 평소보다 느렸다는 사실은 서버 부하나 네트워크 변동으로도 생길 수 있다. 같은 요청을 여러 번 보내 기준 시간을 잡고, 조건을 바꾼 요청에서 약 10초 차이가 반복되는지 대조해야 지연이 SQL 실행에 따른 것인지 판단하기 쉽다.

**아직 정해지지 않은 것**

추적 쿠키의 실제 이름과 값, 데이터베이스 종류, 지연을 일으킬 수 있는 SQL 표현식은 문제 설명에 제시되지 않는다. 그러므로 특정 문법을 먼저 정답으로 적는 대신, 정상 요청의 처리 시간과 입력 변경 후 시간을 기록하면서 유효한 주입 문맥을 찾아야 한다. 이 문제에는 관리자 비밀번호 조회나 로그인이라는 완료 조건이 없다. 아래에는 지연을 직접 확인한 요청과 반복 측정 결과만 풀이로 남긴다.

## 탐색 및 풀이 기록

### 초기 관찰

입력 지점은 상품 페이지 요청의 `TrackingId` 쿠키였다. 원래 값으로 요청하면 HTTP 200, 본문 4304자였고 1.61초 걸렸다. 쿠키 값 끝에 `'`를 붙여도 HTTP 200, 본문 4304자로 **본문이 완전히 같았고**, 1.66초 걸렸다. 작은따옴표 입력만으로는 화면에서 차이를 읽을 수 없었다.

### 실행 과정

같은 쿠키 값 뒤에 PostgreSQL의 `pg_sleep(3)`을 이어 붙여 시간을 비교했다.

~~~sql fragment
<원래 TrackingId>'||pg_sleep(3)--
~~~

정상 요청과 지연 요청을 번갈아 보냈다. 모든 응답은 HTTP 200이었고 본문 길이는 4304자로 같았다.

| 요청 | 응답 시간 |
| --- | --- |
| 정상 | 1.61초, 1.46초, 1.38초 |
| `pg_sleep(3)` | 5.18초, 4.58초, 4.43초 |

지연 요청이 매번 약 3초 더 걸렸다. 이어 완료 조건인 10초 지연을 시험했다.

~~~sql fragment
<원래 TrackingId>'||pg_sleep(10)--
~~~

바로 앞 정상 요청은 1.78초, `pg_sleep(10)` 요청은 11.36초 걸렸다. 지연 요청도 HTTP 200, 본문 4304자였다.

## 최종 결과

10초 지연 요청 후 다시 페이지를 열자 `Congratulations, you solved the lab!` 배너가 표시됐다. 실습을 완료했다.

## 배운 점

본문과 상태 코드가 같아도 SQL 조회가 응답 전에 실행되면 처리 시간이 신호가 된다. 정상 요청과 지연 요청을 반복해 비교하니 네트워크 변동과 약 3초의 의도적인 지연을 구별할 수 있었다.
